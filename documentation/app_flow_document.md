# Wedding CMS Dashboard App Flow Document

## Onboarding and Sign-In/Sign-Up

When a new visitor opens the application, they arrive at the landing page located at the root URL. This page introduces the purpose of the wedding CMS and displays prominent buttons to either sign up or sign in. Selecting the sign-up button navigates the user to a sign-up form where they enter their email address, choose a password, and submit the information. The system then creates a new account with a default role of "USER" and sends a confirmation email if email verification is enabled in the Better Auth configuration. Once the user verifies their email, they are automatically redirected to the sign-in page. If a visitor already has an account, they can choose the sign-in link instead. On the sign-in page, the user enters their credentials and submits them; upon successful authentication via the Better Auth API route, the application sets a secure session cookie and redirects the user into the protected dashboard area. At any point, if the user forgets their password, they can select the "Forgot password" link on the sign-in page, which presents a form to enter their email. Submitting this form triggers an email with a password reset link. Clicking that link brings the user to a password reset page where they enter a new password. Once the reset is confirmed, they can return to the sign-in page and log in with their updated credentials. Signing out is accomplished by clicking the "Sign Out" option in the header or sidebar menu; this action clears the session cookie and returns the user to the landing page.

## Main Dashboard or Home Page

After signing in, the user lands at the dashboard home page at `/dashboard`. The dashboard layout features a persistent header across the top with the site logo, a theme toggle, and a user avatar menu that includes links to account settings and sign out. Along the left side, a collapsible sidebar lists navigation links. For regular users, the sidebar shows "My Wedding" and "Account Settings." For administrators, the sidebar expands to include "Wedding Templates", "User Management", and "Account Settings." The main content area displays welcoming text and summary cards that provide quick metrics—such as the number of wedding templates for admins or an overview of the user’s own wedding details. From this home page, clicking any sidebar item transitions the user to the corresponding section while retaining the header and sidebar for seamless navigation.

## Detailed Feature Flows and Page Transitions

When an administrator clicks the "Wedding Templates" link in the sidebar, the application transitions to the `/dashboard/weddings` page. There, a data table component fetches the list of all wedding templates via the `/api/weddings` endpoint. The table shows each template’s name, status, and last update time. Clicking the "Create Template" button at the top of the page opens a modal form built with shadcn/ui components. The form fields include template name, description, and theme selection. Submitting the form sends a POST request to `/api/weddings` and, upon success, closes the modal and refreshes the data table to show the new entry. To edit an existing template, the admin clicks an "Edit" icon in the table row, which loads the template data into the same form modal. After modifying fields and submitting, the form sends a PUT request to `/api/weddings/{id}`, and the table updates accordingly. Deletion is handled by a confirmation dialog; once confirmed, the app sends a DELETE request and removes the template from the list.

A regular user selects "My Wedding" in the sidebar to navigate to `/dashboard/weddings/my`. This page displays a form populated with the user’s wedding information, such as names, date, venue, and message. The user edits details directly on the page and clicks "Save Changes" to send a PUT request to `/api/weddings/{userWeddingId}`. Upon a successful update, the page shows a brief success notification. If no wedding details exist yet, the user sees a "Create My Wedding" button that opens the same wedding form in a modal. After creating their wedding, they are redirected back to the form page with fields filled.

Administrators also have access to the "User Management" section at `/dashboard/admin/users`. That page uses a data table to list all registered users and their roles. The admin can click an "Assign Role" button next to any user to open a role assignment form in a modal. Selecting a new role and submitting sends a PATCH request to `/api/users/{userId}/role`. Successful updates refresh the user list to reflect the new roles.

Throughout these feature flows, navigation between pages preserves the dashboard shell. Clicking the site logo in the header always returns the user to the dashboard home at `/dashboard`.

## Settings and Account Management

Selecting "Account Settings" from either the header avatar menu or the sidebar navigates the user to `/settings`. This page is divided into sections for personal information and appearance preferences. The personal information section shows fields for name and email, which the user can update and submit. Submitting sends a PATCH request to `/api/users/me` and, on success, displays a confirmation message. The appearance preferences section offers a toggle for light or dark mode; toggling updates the local theme setting and persists it in the user’s profile. If the application had subscription or billing features, they would appear as a separate section below these preferences, allowing users to view plan details and manage payment methods. After saving changes in any section, the user remains on the settings page, and they can click the site logo or a "Back to Dashboard" link to return to the main flow.

## Error States and Alternate Paths

If a user enters incorrect credentials on the sign-in page, the application displays a clear inline error message stating that the email or password is invalid. During sign-up, if the email is already in use or the password fails complexity checks, the form shows an explanatory error beneath the field. When a user attempts to access a protected dashboard route without an active session, the middleware intercepts the request, redirects them to the sign-in page, and optionally displays a notice that they must sign in first. If a regular user tries to access an admin-only page by altering the URL manually, the application checks their role on the server and returns a 403 Forbidden response, which is caught by an error boundary and renders an "Access Denied" page with a link back to the dashboard home. In the midst of a form-based flow, if the network connection drops or the API returns an unexpected error, the UI shows a banner stating "Network error. Please try again later," and the user can retry the action once connectivity is restored.

## Conclusion and Overall App Journey

From the moment a visitor lands on the public site, they can easily create an account, verify their email, and sign in. Once authenticated, they enter a unified dashboard that adapts based on their role. Administrators manage wedding templates and user roles through intuitive tables and forms, while regular users focus on editing their personal wedding details. The settings area lets everyone update their profile and theme preferences, and robust error handling keeps the experience clear and resilient. At any time, users can sign out to end their session. This end-to-end flow ensures that new and returning users always know where they are, how to complete key tasks, and how to recover from errors without losing momentum.
